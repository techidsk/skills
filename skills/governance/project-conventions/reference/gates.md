# 治理检查与交付

目标：新增违规在合并前被看见，存量违规不阻塞日常开发；本地绿等于 CI 绿；验证与提交按影响范围走，记录留给后来的读者。
落地位置：目标项目 `{docs}/agents/contributing.md` 的「测试与交付」「Git 规范」「治理检查」三节（本文改写而成）、`scripts/`、CI 工作流。
模板：[templates/scripts/](../templates/scripts/)、[github-actions-gates.yml](../templates/ci/github-actions-gates.yml)。
下文命令以 npm 为例，pnpm／yarn 按项目替换。

## 告警档

治理类检查（棘轮、白名单）统一分档，三者行为一致：

| 情形 | 默认 | `--strict` |
| --- | --- | --- |
| 出现基线外的新增违规 | 打 ⚠️，退出码 0；CI 里同时输出 `::warning file=…::` 注解 | 打 ❌，退出码 1 |
| 配置错误（基线或白名单缺失、非法 JSON、knip 执行失败） | 退出码 1 | 退出码 1 |
| 存量已被修掉 | 💡 提示可收缩基线，退出码 0 | 同左 |

- 新检查先走告警档；团队稳定后，在 CI 对应命令后追加 `-- --strict` 升为硬闸。
- 告警档不等于可以忽略：PR 里出现的 `::warning` 在 review 中清掉，或在同一提交里写明理由后更新基线。
- 配置错误无条件失败：否则基线丢失会让检查静默变成永远绿。
- 不可逆或静默出错的检查（如密钥扫描、类型检查）直接做硬闸，不进告警档。

## 存量基线只减不增

- 首次接入时把现有违规冻结为基线，之后只拦新增。基线是「已知欠账」，不是许可。
- 修掉存量后，跑 `--update` 把基线调小并随同一提交入库；`--update` 遇到上升会拒绝写入。
- 确需上调时用 `--update --allow-increase`，并在提交正文写明为什么不能避免。
- 基线文件入库，评审时看数字变化：下降为好，上升必须有理由。

## 落地顺序与首次基线

按依赖由浅到深，每装一个就跑一次、提交一次。脚本复制到目标项目 `scripts/`，按文件头「配置」段改常量；在 `package.json` 登记脚本名。

| 顺序 | 检查 | package.json 脚本 | 首次生成基线 |
| --- | --- | --- | --- |
| 1 | 源码 README 白名单 | `"lint:src-readmes": "node scripts/check-src-readmes.mjs"` | `node scripts/check-src-readmes.mjs --init` |
| 2 | ESLint 压制棘轮 | `"lint:suppressions": "node scripts/check-eslint-suppressions.mjs"` | `npx eslint . --suppress-all`，再 `node scripts/check-eslint-suppressions.mjs --update --allow-increase` |
| 3 | 死文件棘轮 | `"lint:unused-files": "node scripts/check-unused-files.mjs"` | 配好 `knip.json` 后 `node scripts/check-unused-files.mjs --update --allow-increase` |
| 4 | 统一入口与对齐 | `"verify": "node scripts/verify.mjs"`，`"test": "node --test"` | 无基线 |

各项注意：

- **压制棘轮**要求 ESLint ≥ 9.24（bulk suppressions）。`eslint --suppress-all` 会把当前所有违规写进 `eslint-suppressions.json`——此后任何人再跑它都会把新增违规悄悄吞进去，棘轮正是为此而设：它比较的是按规则汇总的压制总数，不是文件。
- **死文件棘轮**依赖 `knip.json` 的入口配置。入口不全会把大量活文件误报成死文件：先参照 [knip.example.json](../templates/scripts/knip.example.json) 补全入口（框架约定文件、测试、脚本、worker），启用对应框架插件，再生成基线。用 `knip --include files` 目测结果合理后再冻结。
- **README 白名单**只扫描一个源码目录，默认 `src`，用 `--src` 或常量调整。
- 每个脚本导出纯函数，测试用 `node:test` + 临时目录，裸跑 `node --test` 即可，不依赖项目自己的 stub 或环境变量。测试文件随脚本一起放 `scripts/`。
- 脚本通过文件顶部常量（路径、基线文件名、包管理器命令）适配项目；改完常量跑一遍对应测试。

## verify 与 CI 对齐

- `scripts/verify.mjs` 按清单顺序执行与 CI 相同的检查，全部跑完再汇总失败，一次看到全部问题。推送前跑它，省掉「CI 红了修完再等一轮」。
- CI 工作流里每个检查一步，步骤命令是 `npm run <script>`；不要把多个检查塞进一个 `run` 的 shell 串里，否则无法按步骤定位。
- 对齐用测试守住：`verify-ci-parity.test.mjs` 解析 CI 工作流里的脚本名，断言 `CHECKS` 全部覆盖，并断言 `CHECKS` 里的脚本在 `package.json` 存在。CI 新增检查而 verify 没加，测试红。
- 只属于 CI 的步骤（安装、构建、部署）登记到测试的 `CI_ONLY`；CI 用聚合或变体脚本时登记到 `COVERED_BY`。
- 慢检查可以另立快档（如 pre-push 只跑静态闸和受影响测试），但完整档必须与 CI 一致。
- 告警档步骤在 PR 与手动运行时跑，日常 push 不重复，见 [github-actions-gates.yml](../templates/ci/github-actions-gates.yml)。

## 测试与交付

验证范围按影响面决定，交付如实说明：

- **范围**：只覆盖本次受影响的逻辑、调用方与回归风险。ESLint 先对明确路径跑；全量 lint、测试、构建仅在用户要求、命中合同或门禁、公共配置或依赖广泛变化、定向检查无法界定问题时运行，并先说明依据。
- **复用覆盖**：仍覆盖当前代码的通过结果直接复用；只有新增改动、失败或未解决风险才重跑或扩大。风险已有有效覆盖且必要检查通过即停止，不追求测试数或覆盖率。
- **交付说明**：写实际验证范围、覆盖位置、未验证环节。定向通过不称全量通过；mock 不证明真实闭环；没跑过的不说通过。

测试分流——新增用例的准入：

- **核心闭环**（金额／额度、权限／归属、隐私与公开范围、核心任务从提交到交付、数据保存／恢复／导出，及影响这些结果的幂等、状态、补偿、兼容）：核心行为有覆盖缺口时补测试，从真实入口核对输入、处理、持久化与用户可见结果，覆盖本次关键失败与恢复。核心 Bug 的回归测试应旧实现失败、修复后通过。
- **普通改动**：用已有检查与人工验收；新增功能、公共函数、有分支、重构或修 Bug 本身都不是补测试的理由。临时复现不自动保留为测试。
- **先复用再补**：先维护旧预期、复用现有测试；类型、lint、schema 已准确覆盖同一错误时不补。补测须说清哪条核心行为会错、如何触发、现有覆盖缺什么，并在最小有效边界补。
- **不为凑数搬测试**：行为变更维护旧预期，功能删除移除相关测试；失败区分回归、合同变化与夹具问题，不靠删断言、skip、强退变绿。清理无效测试时不搬家、不弱化断言凑数，也不为清理加测试框架、mock 基建或新门禁。
- 注入时钟与 I/O，避免模块单例、真实重试等待与 import 时启动外部连接；固定文案、装饰样式不新增用例。

长期保留的检查脚本须写明要防的具体回归、由哪个流程执行、失败后如何处理；一次性盘点与排查脚本放被忽略的本地目录，任务完成后清理。

## Git 规范

- **标题**：`<type>(<scope>): 中文结果`，type 小写，scope 为模块；一条提交一条主线。格式由 commit-msg 钩子或检查脚本强制，语义靠 review。
- **正文就是 changelog**：不单独维护变更日志文件时，`git log` 就是变更记录，正文只写 diff 读不出来的东西——一句话结论、**为什么**这么做、**否掉了什么方案及原因**、**代价与取舍**、怎么验证的、未完成项（写「未完成：」）。
- `fix` 必写根因；`refactor` 必写动机、收益与否决的方案；`feat` 涉及迁移、线上行为、新接口或新依赖时必写。标题已足够时省略正文，空洞正文比没有更糟。
- 正文手动折行约 80 列（中文算 2 列）；正文不用 emoji 或符号装饰；路径与符号用反引号。
- **做完一项提交一项**：多项任务逐项验收后单独提交，每条提交一条主线，不攒成一个大提交；是否推送另问。
- **并行会话下按路径提交**：多个会话共用一个工作区时，只提交自己改的文件——`git commit --only -- <paths>`；提交前用 `git diff -- <paths>` 确认没有夹带别人的 hunk，不用 `git add -A`、`git commit -a`。
- 提交、推送、合并都不构成发布授权；发布与版本号由人决定。
