# 文档治理

目标：人和 Agent 在一处查到当前有效规则，读得少、不读到过期内容。
落地位置：目标项目 `AGENTS.md`（入口）、`{docs}/README.md`（索引）、`{docs}/agents/contributing.md` 的「文档规范」一节（本文改写而成）。
模板：[AGENTS.md](../templates/AGENTS.md)、[docs-README.md](../templates/docs-README.md)、[check-src-readmes.mjs](../templates/scripts/check-src-readmes.mjs)。

## 入口文件

- `AGENTS.md` 只放两类内容：对所有任务都成立的全局短规则；「改什么之前读哪份」的指针。细则一律下沉到 docs 正本。
- 指针写成行为触发：「修改 X 前，读 [Y](路径#锚点)」。带锚点时读该节全文含子节；不要写「详见某文档」这类没有触发条件的链接。
- 入口开头声明：链接是必须执行的阅读指令，跨领域任务读全部命中项，不遍历未命中文档。
- `CLAUDE.md` 只写 `@AGENTS.md` 一行导入，不复制正文；两份规范会漂移。
- 入口末尾留「规范文件本身」一节，写明：全局规则只在 AGENTS.md 维护、业务条目只写何时读哪份、移动规则时同步入链与检查。
- 代码或 lint 已说清的规则不进入口；入口膨胀时先问「这条能不能交给工具」，再问「这条是不是只在某个领域生效」。

## docs 目录

- 文档根只有一个（通常 `docs/`），按业务域分子目录；根目录不另建文档目录，Agent／Skill 入口留规定位置。
- 新增文档必须登记 `docs/README.md`；索引只导航，不承载第二份规则。
- 文件名 `kebab-case`；长期运维手册用 `-ops.md`；日期只用于公告与证据，不给长期规则建日期副本。
- 链接用相对路径；引用代码路径时注明基准目录。
- 文档按职责分工，各有正本：通用指南管设计判断；工程约束管接入方式；领域合同管行为、权限、兼容；运维手册管前提、步骤、恢复与完成判据。

## 每条规则一份正本

- 同一规则只写一处，其他地方链接过去。想在第二处复述时，改成链接。
- 先更新已有正本；只有独立任务分支或独立交付边界才拆新文件。
- 新文档开头写适用范围、何时读、依赖哪些文档。规则、例外、兼容与验收放在一起；完成判据可核验。
- 领域文档只补领域额外约束，引用通用规则而不重述。

## 只写源码表达不了的约束

- 源码持有 API、配置值、CSS 数值、命令；文档保留源码解释不了的约束：为什么、边界、例外、跨系统合同、外部事实。
- 生成物（OpenAPI、schema）是字段与枚举的事实源，文档不另维护一份全集。
- 代码注释同理：只写护栏（执行顺序、资源所有权、外部协议的反直觉事实）；方案对比和历史妥协归提交正文。

## 长期规则的生命周期

- **原位更新**：规则变了就改原文，不追加「更新于」段落，不新建历史副本、整理报告、时间线。
- **完成后提炼再删**：Spec、方案、计划完成后，只把仍影响当前维护的规则与必要原因并入正本，其余删除；历史去 Git、Issue、PR 追溯。
- **不补历史账**：清理旧文档不以补关闭 Issue、补验收记录为前提；旧文档里的「待验／未完成」不自动变成新待办。
- **保留真正的限制**：仍有依据的未解决缺陷、权限／隐私／计费／兼容边界和必要发布门禁留在正本，不因删文档而宣称已解决。
- **archive 不作依据**：`archive/` 里的内容不当现状。清理前先把其中唯一有效的约束迁回正本；保留有用途的发布公告、运维审计、授权材料。已应用的数据库迁移 SQL 保持不变。
- **收尾检查**：有效规则与例外无遗漏；入口、索引、入链与锚点有效（含源码注释里的链接）；业务语义不变；未实测的不写成已通过；差异、链接与格式无误。

## src/ 下的 README

源码目录里的 README 只允许三类：

1. 指向 docs 正本的维护入口；
2. 该目录的边界或准入规则（谁可以放进来、谁不可以依赖）；
3. 无法写成注释的数据文件出处（生成来源、更新方式）。

功能介绍、文件清单、业务合同、运维步骤放 docs 正本。新增 README 须登记到白名单（默认 `scripts/src-readme-allowlist.json`），由 `check-src-readmes.mjs` 检查；接入顺序见 [gates.md](gates.md)。

存量 README 接入时：先 `--init` 生成白名单冻结存量，再逐份判断——属于三类的留下，其余迁入 docs 后删除并从白名单移除。

## 材料归属

按当前用途决定放哪里，不因叫 Spec、带日期或花过时间就长期保存。

| 位置 | 保留内容 |
| --- | --- |
| 仓库领域文档 | 当前行为与重要约束、必要的决策原因、兼容边界、可复用的运维与验收方法；随实现更新 |
| Issue／PR | 需求、方案讨论、任务拆分、本批交付记录；不要求随实现追溯改写 |
| 仓库规定目录 | 实际使用的测试代码、fixture 与基线、必要的发布元数据、审计与授权材料 |
| 被 Git 忽略的本地目录 | 临时脚本、原始响应、一次性截图与快照；不提交，也不自动上传到 Issue |

- 调研在对话中交付；报告、草稿和取样材料不落仓库。已采用的结论随实际改动进入对应正本。
- 临时起草前确认目录已被 Git 忽略（`git status` 不应出现）。
- 仓库里不保存 Issue 全文、任务状态镜像或逐次交付报告。简单改动直接交付，不自动创建文档或 Issue。
- 文档归属不增加提交、推送或外部写入的授权。

## TODO 文件（可选）

若项目用 `todo.md` 暂存「尚未进 Issue 的阻塞或待决策事项」：只收当前做不了的事，已建 Issue 的在 Issue 维护；每条写背景、价值、做法、阻塞点、完成判据，无上下文的人也能执行；完成、决定不做或前提失效就删整条，删除动作独立 `docs(todo):` 提交。没有这个文件的项目不引入。
