# 目录与架构约束

目标：让业务逻辑只有一个落点、依赖只有一个方向，读代码的人从目录名就能判断一段代码该在哪、能依赖谁。
本文写判断；方向与 barrel 由 lint 强制，环由 dependency-cruiser 兜底，装法见文末。

## 1. 三层职责（Thin Router, Fat Service）

| 层 | 典型目录（占位，落地时替换） | 放什么 | 可以依赖 |
| --- | --- | --- | --- |
| 入口薄层 | `{{入口薄层目录}}`（页面、HTTP 路由、RPC/Action、CLI、队列消费者） | 入参解析与校验、鉴权、调用业务模块、把结果转成响应 | 业务模块、基础设施 |
| 业务模块 | `{{业务模块目录}}/<domain>` | 业务规则、协议、服务与用例、读写数据库 | 同层其他模块、基础设施 |
| 基础设施 | `{{基础设施目录}}`（数据库客户端、缓存、日志、队列、通用工具） | 与具体业务无关的能力 | 只依赖自己和第三方 |

依赖只能向下：入口 → 业务模块 → 基础设施。共享 UI 组件（`{{共享组件目录}}`）属于入口一侧，同样不得依赖入口层。

**为什么**：多个入口（Web、API、脚本、队列）要复用同一份业务逻辑；逻辑写进入口层就只能被那一个入口用。反向依赖会把路由形态、框架上下文倒灌进业务逻辑，业务模块因此无法在脚本或测试里单独运行。

**判据：这段代码换个产品还成立吗？** 成立进基础设施，不成立进业务模块。有自己的业务规则、角色语义或契约测试的，一律是业务。「组件和模块都要用它」不是进基础设施的理由，因为入口层本来就允许依赖业务模块；只有「与业务无关」才是。基础设施不是「暂时不知道放哪」的落点，这样落进去的文件会让目录失去领域线索。

## 2. 业务模块内部

一个领域一棵树：领域大到装不下时拆子目录（`<domain>/<sub>/`），不用连字符前缀在同一层平铺。子模块内部沿用同一套文件分工（按需创建）：`service`（业务逻辑）、`actions` 或 `handlers`（入口适配）、`schema`（校验与类型）、`queries`（复杂查询）。

**跨领域编排层**：一个用例要串起多个领域（下单、发布、结算）时，单独放进编排文件或子模块，不寄生在某个领域 service 里。否则它会被一路 import 进越来越多的模块，而那不是该领域的逻辑。

| 层 | 是什么 | 可以调谁 | 谁调它 |
| --- | --- | --- | --- |
| 领域 service | 只碰自己领域的数据，可复用可单测 | 同模块内 + 基础设施 | 任何人 |
| 编排 | 跨领域用例 | 多个领域 service | 只有入口适配层 |
| 入口适配 | 路由、Action、CLI | 编排或单个 service | 框架 |

编排的判据：依赖 ≥3 个别的模块，且不被任何别的 service import。数依赖时排除「读侧投影」——只导入 DTO 映射函数、select 常量、纯类型的不算依赖，机械按数量判会把它们误认成编排。

模块之间的互相调用方向目前靠 review 把关；需要时再在 `layerZones` 里加模块级 zone。

## 3. 禁止新增模块级 barrel

直接 import 到具体文件（`@/modules/orders/service`），不新增 `index.ts` 再导出。

**为什么**：barrel 的再导出会把被导出文件的整张依赖图连进每个导入方。其中混入数据库、鉴权等仅服务端依赖时，客户端导入会在构建期失败；它还多一层入口，容易形成环。纯常量的聚合导出同样不开例外，统一直接导入。

`project/no-barrel-file` 拦入口文件，`no-restricted-syntax` 拦 `@/modules/<name>` 形状的导入。落地时已有的 barrel 写进 `allow`，每条注明理由，只减不增。

## 4. 文件粒度

- **单文件超过 800 行时按职责边界拆分**；找不到边界时在文件头写明不拆的原因（例如「单一状态机，拆开会把转移规则分散到多处」）。`max-lines` 只管行数，边界判断靠人。
- **逻辑默认写在唯一调用处。** 拆到新文件、导出或上移共享层须有当下的理由：出现第二个调用方、需要隔离依赖、需要独立测试，或超过 800 行后找到了职责边界。「将来可能复用」不算理由；理由消失后收回原处。

**为什么**：过早抽出的函数没有第二个调用方来校验它的形状，常常带着只有第一个调用方才用得上的参数；读代码的人还要多跳一个文件才能看到完整逻辑。

组件同理：页面私有组件放页面旁（`_components` 或同级），多个页面实际共用时才上移到共享目录，并由页面通过明确入口调用；共享组件不得反向引用页面私有实现。需要 `../../../` 才能够到目标，往往说明共享代码停在了路由树里，应上浮后用别名导入。

## 5. 常量归属

- 业务规则、协议版本、展示映射、领域限制放所属业务模块；跨领域调用方直接导入该领域的纯文件。
- 与业务无关的通用常量（上传上限、会话基础配置、构建信息）放基础设施的常量目录；领域引用它，不另复制数值。
- 同一领域默认一个 `constants.ts` 分段书写。少量常量、一次需求或一个调用方不构成独立文件的理由；形成独立子领域、需要隔离依赖或超过行数上限时才拆。
- 只被单个实现使用的局部常量就近声明；跨入口必须一致的规则由领域文件持有。
- 客户端与服务端共用的文件保持纯依赖：只放纯工具、类型与枚举，不引入 service、数据库、鉴权实例或服务端 SDK。

**为什么**：常量按「谁拥有这条规则」归属，才能在改规则时找到唯一位置；按「是不是纯函数」归属会让同一规则散在几处。

## 6. 依赖环基线

用 dependency-cruiser 的 `no-circular` 检查环，把存量环生成为基线文件，CI 用 `--ignore-known` 只拦新增。基线文件提交进仓库，只减不增：修掉环后重新生成，让数字变小。

**为什么**：存量代码通常已有环，直接开硬闸会让规则被整体关掉；基线冻结存量，新增的环在引入当天就被发现，根因清晰。命令与配置见 `templates/dependency-cruiser.cjs` 文件头。

## 映射到目标项目

落地第一步是填这张表（摸底阶段完成）：

| 占位 | 含义 | 常见取值 |
| --- | --- | --- |
| `{{入口薄层目录}}` | 入口层目录（相对源码根，下同） | `app`、`routes`、`pages`、`cli` |
| `{{业务模块目录}}` | 业务模块根 | `modules`、`domains`、`features` |
| `{{基础设施目录}}` | 无业务基础设施 | `lib`、`infra`、`shared` |
| `{{共享组件目录}}` | 共享 UI（无前端则略） | `components` |

项目只有两层（如纯后端服务）就只保留「业务模块 → 基础设施」的 zone；目录名不同就只改 `eslint.config.snippet.mjs` 的 `layerZones` 与 `dependency-cruiser.cjs` 的 `SRC_DIR`。项目已有违规时先冻结存量（`eslint --suppress-all` + 环基线），不要因为存量改写规则。

## 装法

- 分层 zones：`templates/eslint/eslint.config.snippet.mjs`（`import-x/no-restricted-paths`；zones 只在一处声明，专项限制展开它再追加）。
- barrel：`templates/eslint/no-barrel-file.mjs`。
- 环：`templates/dependency-cruiser.cjs`。
- 测试里的依赖方向与源码一致：纯领域测试留在业务模块，组合界面与领域的测试归界面功能；不为集成测试给业务模块开放对入口层的反向依赖。
